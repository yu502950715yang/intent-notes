# 非代码工作目录的决策笔记设计

日期：2026-10-15（取自仓库最后一次提交；若实际日期不同只改文件名）
状态：待评审

## 背景

intent-notes 现在的形态把「笔记」绑在 git 仓库上：

- 门禁 3 校验 `## 涉及仓库` 段里的仓库、分支、commit，事实实时查 git
- `init` 在目标目录**无条件** `git init`（目标无 `.git` 时）
- 笔记树固定在 `<项目根>/.agents/notes/`
- `backfill` 整条链路依赖 commit

新场景：在**非代码的工作目录**（需求 / PRD 文件夹）里也留决策笔记。这些目录不是 git 仓库，使用者（需求人员）不使用 git，也不会敲命令。

## 目标与非目标

目标：让「改需求」这件事能像「改代码」一样留下决策笔记（为什么这么定、否决了什么），且不要求使用者懂 git。

非目标：跨 git / 非 git 的统一作用域（不做）；外部文档系统（Confluence / 飞书）锚点（不做）；无 git 版 `backfill`（不做）。

## 调查结论（设计依据）

| 层 | 与 git / 目录的耦合 |
|---|---|
| 门禁 1 结构、门禁 2 格式 | 只吃 notes 根参数，与 git 无关 |
| 门禁 3 锚点 | 强耦合：每个 `repos` 条目必须是独立 git 仓库根，fail-closed |
| `init` | 目标无 `.git` 时无条件 `git init`；非 0 退出即中止 |
| `backfill` | 整条链路依赖 commit |
| 六分类、四生命周期、模板骨架 | 与代码无关，天然适用 |
| skill 自身部署位置 | 已解耦，装在哪都可用 |

关键推论：**「能否适配非代码目录」本质上等于「那个目录是否（或能否成为）git 仓库」。**

## 采用方案 X：由 agent 代劳版本控制

目标目录照常 `git init`（沿用它现有行为），agent 负责建仓库、提交产物、写笔记。使用者依然不接触 git。

选它的理由：**零程序改动**，且能力比自研快照锚点更强——保留完整历史、`backfill` 可用、锚点仍是 fail-closed 的 commit 校验。

### 前置条件（部署要求，与 Node 同级）

1. 机器有 **Node ≥ 22.18**（跑 agent 已隐含此项）
2. 机器有 **git**（`git --version` 可用）
3. `git config user.name` / `user.email` 已配置（否则首次 commit 失败）

git 由使用者机器**预先安装**（winget / choco / PortableGit 均可）。不满足前置条件时，`init` 会在 `git init` 处 fail-closed 退出。

### 硬约定：agent 不自行安装软件

git 不可用时：**不要下载或安装任何软件**。停止初始化，如实报告原始错误，给出两条出路（用户级安装 git / 改用备选方案 B），由人决定。

理由：让 agent 自主下载并运行二进制工具是不可逆且越界的行为；本 skill 的职责是记录决策，不是管理系统依赖；受管控电脑上擅自安装会引发 IT 问题。

## 详细契约

### 1. `SKILL.md` 的 description

现状的命中条件是「改了行为、架构、跨文件契约、流程与工具链、测试策略，或落盘 / 网络 / 配置格式」——**改需求文档一条都不命中**，skill 不会被加载，整条链路断在第一环。

`tests/templates.spec.ts` 的两条测试锁定了这段文案，改写**必须逐条守住**：

| 断言 | 要求 |
|---|---|
| frontmatter | 仍以 `---` 开头，`name: intent-notes` 仍在 |
| 长度 | `description:` 的值 > 40 字符 |
| 判据词 | 必须含 `改了行为`、`架构`、`跨文件契约`、`流程与工具链`、`测试策略` |
| 初始化触发 | 必须含 `初始化`，且含精确字符串 `用户说「给这个项目建决策笔记」` |
| 禁用词 | 不得出现 `知识库` |

精确文案（**单行，不可换行**）：

> 在交付项目或工作目录里留下并维护决策笔记（Agent Notes）。当一次改动改了行为、架构、跨文件契约、流程与工具链、测试策略、需求方向或范围，或落盘/网络/配置格式时，就在当前项目的 .agents/notes/ 下新建或更新一篇笔记；也用于在已有项目里初始化这套笔记体系（用户说「给这个项目建决策笔记」或「给这个项目建笔记体系」时）。需求 / 文档类工作目录即使不是 git 仓库也适用（由 agent 代劳版本控制，见 references/plain-directory-mode.md）。纯机械改动（格式化、无歧义重命名、不改行为的样式或依赖补丁、照已有契约的常规 CRUD）不写。

### 2. 新增「第 0 节：会话开始先查改动」

放在现有第一节「先判要不要写」之前。门禁不会自己启动，这是「该写却没写」唯一的补丁：

1. `git status --short` —— 有未提交改动，说明产物被改过，必须走第一节判定
2. `git log --oneline -5` —— 有未记录的新提交，同样走第一节判定
3. 跑 `node <skill-dir>/scripts/verify-note-anchors.ts <工作目录>`，红了先处理再谈本次任务

### 3. 硬规则 6 补充（同一仓库的两次提交）

> 产物改动**先提交**（得到 commit）→ 再写笔记（锚点引用该 commit）→ 笔记单独提交。笔记的 commit 锚点只能指向已存在的 commit。

### 4. 新增 `references/plain-directory-mode.md` 大纲

- **适用与前提**：非代码工作目录；机器有 git；目录必须在**本地磁盘**（同步盘 / 网盘的同步会损坏 `.git`）
- **部署前自检**：`node --version`、`git --version`、`git config user.email`——先自检再 init，让失败信息是人话而不是裸命令错误
- **初始化**：`node "<skill-dir>/scripts/init.ts" "<目录>"` → `git branch --show-current` 确认分支名（可能是 `master` 而非 `main`，笔记要照抄）→ 缺 `user.name` / `user.email` 先配
- **必补 `.gitignore`**：`~$*`、`.~lock.*`、`*.tmp`——Office 锁文件不排除，每次打开文档都会产生假改动，这是最影响信任的一条
- **每次改动流程**：改产物 → `git status` 看范围 → 判要不要笔记（第一节）→ `git add` **指定文件** → commit（中文一句话）→ 写笔记 → 提交笔记
- **两个坑**：第一篇笔记之前必须先有一次提交（否则分支 ref 尚不存在，门禁会红）；commit 前先看 status，别把密码 / 原始素材提交进去
- **代价**：Word / Excel / PPT 是二进制，每次改动全量入库，仓库会膨胀（PRD 量级可接受）
- **git 缺失时**：只报告不安装，见上「硬约定」

### 5. 其余三处

- `SKILL.md` 第五节「详细规则（按需读取）」列表加一行，指向 `plain-directory-mode.md`
- `bootstrap-existing-project.md`：非代码工作目录下，阶段 2 无需铺子仓库指针；阶段 3 历史收割不适用（没有 commit 历史可收割）；并指向上面的新 reference
- `templates/notes-readme.md`：补一句「本目录可能不是 git 仓库，由 agent 代劳版本控制」

## 验证方式

1. 在一个真实需求文件夹上跑 `init`，确认 `.git`、`.agents/notes/` 骨架、`.agents/intent-notes/config.yml`（`repos: - path: .`）落盘正确
2. 提交一次产物 → 写第一篇笔记（锚点用该 commit）→ 门禁 3 绿
3. 修改产物 → 按第 0 节 `git status` 应当报出改动 → 判定是否留笔记（这一环是**没有门禁保护**的，必须实测）
4. 回归：`npm test`（100 用例）+ `npm run typecheck`——因零代码改动，预期全绿，用于确认没有误伤

**已知环境阻碍**：本机 `pwsh` 启动即失败（exit code 3221225794 / `STATUS_DLL_INIT_FAILED`），`npm` 脚本与 git 命令均无法执行。实施与验收前需先修复。

## 备选方案 B（未采用，存档）

适用条件：git 无法供给（机器无法安装 / 受管控），或用户拒绝在任何工作目录建 `.git`。

设计要点（已完整论证，需要时不必重新推导）：

- `config.yml` 支持 `dirs:` 段（与 `repos:` 并存，**不引入全局 `mode` 开关**，避免「模式与内容不一致」这一新的 fail-closed 漏洞面）
- 笔记段名 `## 涉及范围`，门禁 3 **同时接受** `## 涉及仓库`（现有笔记零回归）；两者同时出现判红
- 文件锚点行：`- \`prd\` 文件 \`需求/登录改版.md\` @ \`sha256:<64 位 hex>\``；**哈希必填**
- 为何哈希必填：无 git 时内容被就地覆盖，V1 只存在于笔记里；只校验文件存在会让「第二版需求」静默通过，而门禁查不了「该写却没写」。哈希是让「需求变过」被机器发现的唯一信号
- 红之后的动作是**三选一**：措辞变更 → 更新哈希；事实变更 → 就地改笔记；方向翻转 → 新开一篇并互链（对应现有硬规则）
- `init` 新增 `--no-git`：不 `git init`、不探测子仓库、不写 `.gitignore`，改写 `dirs:`；默认行为一个字节不改
- `backfill` 在无 git 目录明确不支持（fail-closed 说清，不伪造降级行为）
- 改动面：4 个程序文件约 150 行 + 新测试 + 上述文档全量
- 风险：哈希假红（行尾差异、同步盘回写、编辑器重写整文件）；每次会话开始跑门禁的成本随笔记数线性增长

## 风险与已知限制

1. **触发是单点**：需求人员只会说「改成 B」，不会说「记一篇笔记」。description 措辞 + `AGENTS.md` 规矩 + 第 0 节三管齐下，但「该写没写」**没有任何门禁**能挡
2. **git 前置条件**：使用者的机器必须预装 git；这不是「零成本」，而是把成本前置成一次装机动作
3. **同步盘禁用**：需求文件夹若在 OneDrive / 企业网盘上，`.git` 有损坏风险，本方案不适用
4. **二进制膨胀**：Office 文档每次改动全量入库
5. **无远端**：本方案只在本地做最小提交，不推远端、不引入分支工作流

## 不做的事

- 不加 URL / 外部系统锚点（第 4 种锚点类型）
- 不做无 git 版 `backfill`
- 不接线 `sources:`（现有 config 里写入但**代码中没有任何消费者**的死配置）
- 不改门禁 1 / 2，不改六分类闭集，不改笔记树结构
